# Work Distribution Across Instances

**Question:** when N processes of dag-worker-go run against the same shared storage (in-memory-per-process is trivially single-owner, so this is really about Redis / Memcached / PostgreSQL backends), how do they divide up the pool of ready nodes without double-dispatching, without a hot-key bottleneck, and without a rebalancing storm every time an instance joins or leaves?

This dossier surveys five real strategies, the membership substrate each one needs, the fencing mechanism that makes any of them safe under process pauses, and quantifies contention on the two SQL/KV backends the library must support (Redis, PostgreSQL). It ends with one recommended hybrid design and a no-API-break migration path from a v0.1 single-partition implementation.

---

## 1. Pure pull / competing consumers

Every instance runs the same loop: atomically pop the next ready item from one shared collection. There is no membership table, no ownership map, no rebalancing logic — the storage's atomicity is the only coordination primitive.

### 1.1 Reference implementations

**SQS.** A `ReceiveMessage` call marks the message invisible for a `VisibilityTimeout` (default 30s, extendable up to a hard 12-hour ceiling via `ChangeMessageVisibility`); if the consumer doesn't call `DeleteMessage` before the timeout lapses the message reappears for any consumer to re-receive. SQS is explicit that this is at-least-once, not exactly-once: "there's no absolute guarantee that a message won't be delivered more than once during the visibility timeout period" — two consumers can race under network delay or clock skew, and the workload must be idempotent as a result. Standard queues additionally cap **in-flight (received-but-undeleted) messages at roughly 120,000**; past that, `ReceiveMessage` returns `OverLimit` for short polling or silently returns nothing for long polling until the backlog drains — a concrete existence proof that a single unpartitioned ready-set has a *contention ceiling* even in a system engineered for this exact job. [AWS: SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)

**Sidekiq (Redis, `BRPOP`).** The default fetcher does a blocking `BRPOP` off the queue list — O(1), and Redis guarantees only one blocked client wakes per pushed element, so this is race-free at the primitive level. The cost is paid on crash: pop already removed the job from Redis, so a hard kill between `BRPOP` and job completion loses the job outright. Sidekiq Pro's `super_fetch` fixes this the way SQS does — it moves the job into a private "working" list atomically (`BRPOPLPUSH`) and only trims it on success; on worker startup it scans for orphaned working lists whose owner's heartbeat (a TTL'd Redis key) has expired (60s default) and requeues them. The GitHub issue tracker records the downside directly: raising the per-queue poll timeout was needed because many `BRPOP` connections against many queues burn idle CPU on the Redis server unless the block duration is tuned up. [Sidekiq Reliability wiki](https://github.com/sidekiq/sidekiq/wiki/Reliability) · [BRPOP CPU issue #4855](https://github.com/sidekiq/sidekiq/issues/4855)

**Asynq (Go, Redis).** The dequeue is one Lua script — atomic RPOPLPUSH-plus-bookkeeping — moving a task id from the pending list straight into an **active** list and a **lease** sorted-set scored by an absolute deadline:

```lua
-- dequeueCmd (asynq internal/rdb)
if redis.call("EXISTS", KEYS[2]) == 0 then
  local id = redis.call("RPOPLPUSH", KEYS[1], KEYS[3])
  if id then
    local key = ARGV[2] .. id
    redis.call("HSET", key, "state", "active")
    redis.call("HDEL", key, "pending_since")
    redis.call("ZADD", KEYS[4], ARGV[1], id)   -- lease deadline = now + LeaseDuration
    return redis.call("HGET", key, "msg")
  end
end
return nil
```

`LeaseDuration` defaults to 30s. A background *recoverer* goroutine periodically `ZRANGEBYSCORE`s the lease set for entries whose score has passed and runs a companion `requeueCmd` script that `LREM`s from active, `ZREM`s from the lease set, and `RPUSH`es back to pending — exactly the SQS visibility-timeout pattern, reimplemented client-side because Redis has no native per-item TTL-with-requeue primitive. [Asynq `rdb.go`](https://github.com/hibiken/asynq/blob/master/internal/rdb/rdb.go)

**Redis Streams consumer groups** are the vendor-native version of the same idea and are directly reusable as a claim primitive: `XREADGROUP ... STREAMS mystream >` atomically assigns unread entries to a named consumer and records them in a **Pending Entries List (PEL)**; `XCLAIM`/`XAUTOCLAIM` let any consumer sweep the PEL for entries idle longer than a threshold and reassign them, incrementing a per-entry delivery counter you can use as a poison-pill circuit breaker. This is a closer structural match to dag-worker-go's "claim → ack success/error → reclaim on timeout" life-cycle than a plain list, and it comes with observability for free (`XPENDING`, `XINFO CONSUMERS`). [Redis Streams docs](https://redis.io/docs/latest/develop/data-types/streams/)

**River (Go, PostgreSQL).** Uses `SELECT ... FOR UPDATE SKIP LOCKED` to let N competing workers poll the same `river_job` table without blocking each other — `SKIP LOCKED` (added in PostgreSQL 9.5) makes each worker skip rows another transaction already has row-locked instead of queueing behind them, so the claim is O(rows-examined-until-first-free-row) rather than O(waiters). River's producer batches this at the process level: one producer per process claims a batch and hands jobs out over goroutines internally, trading one round trip per batch instead of per job. [River announcement](https://riverqueue.com/blog/announcing-river) · [Netdata: SKIP LOCKED for queues](https://www.netdata.cloud/academy/update-skip-locked/)

A representative claim query, generalized from this family (not verbatim from any one project):

```sql
WITH claimed AS (
  SELECT id
  FROM   dag_nodes
  WHERE  status = 'ready'
    AND  scope  = $1
  ORDER  BY priority DESC, created_at
  FOR UPDATE SKIP LOCKED
  LIMIT  $2
)
UPDATE dag_nodes n
SET    status = 'in_progress', claimed_by = $3, claim_deadline = now() + $4
FROM   claimed
WHERE  n.id = claimed.id
RETURNING n.id, n.payload;
```

Airflow's HA scheduler design is worth citing as confirmation that this pattern generalizes beyond queues to arbitrary "many schedulers picking rows out of one metadata DB" workloads: with `>=2` schedulers, Airflow relies on the DB issuing `SELECT ... FOR UPDATE` on the relevant rows so "the scheduler that acquires the lock first runs the task"; the docs flag that MySQL 5.x lacks `SKIP LOCKED`/`NOWAIT` and explicitly forbid running more than one scheduler against it, which is corroborating evidence for treating `SKIP LOCKED` support as a hard backend requirement rather than a nice-to-have. [Apache Airflow scheduler docs](https://airflow.apache.org/docs/apache-airflow/stable/administration-and-deployment/scheduler.html)

### 1.2 What pull-based competition gets right and where it breaks

**Right:** zero membership protocol, perfectly self-balancing (an instance that's faster or has spare capacity naturally claims more), trivially handles instances joining/leaving — nothing to rebalance because nothing was statically assigned. **Breaks:** every claim serializes through one hot key/table region, so throughput has a ceiling that's a property of the storage engine, not the workload (quantified in §6); and there's no locality — an instance may claim node 3 of a DAG one tick and node 3,004,102 of an unrelated DAG the next, so any per-DAG in-memory index (topological order cache, dependency counts) is useless across claims and must be reloaded from storage or reconstructed from edges every time, which is exactly the O(1)/O(log n) discipline the brief wants to avoid violating implicitly through cache-miss amplification.

## 2. Static partitioning by scope

Each of the N instances is statically assigned a disjoint subset of **scopes** (dag-worker-go's own namespacing primitive), and only claims work within scopes it owns. This is the "shard by tenant" pattern common in multi-tenant SaaS schedulers.

**Mechanism.** A simple deterministic function — `hash(scope) mod N`, or a range partition if scopes are lexically ordered and skew-aware bucketing is desired — decides ownership; each instance filters its claim queries by `WHERE scope = ANY($owned_scopes)`.

**What it buys.** An instance can keep a *hot in-memory index per scope it owns*: adjacency lists, in-degree counters, a ready-heap ordered by priority — genuinely O(1) node-ready lookups with zero storage round trips for the common case, falling back to storage only for durability and for other instances observing status transitions. This is the strongest argument for the pattern given the brief's O(1)/O(log n) mandate: pull-based competition cannot give you this because ownership of any given node is not sticky.

**Where it breaks — head-of-line blocking and skew.** If scope assignment is static and one scope's DAG is enormous (say, a million-node batch import) while the other N−1 scopes are trickling small graphs, one instance is pinned at 100% while N−1 sit idle — the library cannot borrow their capacity because ownership is a hard partition, not a preference. This is precisely the failure mode the brief calls out, and it is why static partitioning is never used alone at scale: Kafka consumer groups statically assign whole partitions to consumers *within a rebalance epoch*, but Kafka's own docs and KIPs are full of guidance to over-partition (many small partitions, not few big ones) specifically to keep the static-assignment granularity fine enough that skew self-corrects on the next rebalance — an implicit admission that raw static partitioning doesn't cope with skew and needs a finer unit of assignment to approximate load balancing. **The fix that generalizes this pattern (§3) is: partition into far more virtual shards than there are instances, then assign multiple shards per instance and rebalance shard-to-instance mapping (not node-to-shard) when membership changes** — which decouples the two skew sources (which scope is hot; which instance is hot) instead of conflating them into one static map.

**Split-brain hazard specific to this design.** Two instances can each believe they own scope `S` during a membership transition (a rebalance in flight, a network partition where the old owner hasn't yet noticed its lease expired) and both claim from `S`'s ready-set simultaneously. Because the *underlying claim* is still an atomic storage operation (an UPDATE with `SKIP LOCKED`, or an `HSETNX`), double-**claim** of the *same node* is prevented by the storage primitive regardless of scope ownership confusion — but double-**scanning** by two owners wastes work and, without a fencing token (§5), a stale owner can still write a stale status transition after a newer owner has already completed and moved the node forward, corrupting the DAG's state machine. Ownership assignment must therefore be advisory for *routing which instances scan which scopes* (an optimization) while the *claim* itself stays a compare-and-swap keyed by node id with a fencing epoch, never trusted from partition ownership alone.

## 3. Hash partitioning into virtual partitions with leased ownership

The Kafka/Redis Cluster pattern: don't partition by scope 1:1 to instance; partition the whole keyspace into **many more virtual partitions than there are instances** (Redis Cluster fixes this at **16384** hash slots regardless of cluster size — "effectively setting an upper limit for the cluster size of 16384 master nodes," with each key's slot computed as `HASH_SLOT = CRC16(key) mod 16384`, and hash tags `{...}` letting related keys be pinned to the same slot for multi-key atomicity — [Redis Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)), then lease *groups* of these virtual partitions to instances, and only rebalance the lease→instance mapping (cheap: move a handful of small units) rather than the partition function itself (expensive: everyone's assignment shifts).

This section is the deep dive the brief specifically asked for. Five hashing strategies solve "which virtual partition does this key belong to" with different tradeoffs; all of them are then wrapped in the same lease-and-fence machinery from §5.

### 3.1 Karger et al. consistent hashing (1997)

Karger, Lehman, Leighton, Panigrahy, Levine, Lewin, "Consistent Hashing and Random Trees," STOC 1997. Each bucket is hashed to several random points on a unit circle ("virtual nodes"); a key hashes to a point and walks clockwise to the first bucket point it meets. Removing/adding one bucket only reassigns the keys that fell in its arc — the foundational **monotonicity** property that makes rebalancing local. The catch, stated plainly by Lamping & Veach who benchmarked against it directly: to get a coefficient-of-variation of bucket sizes down to ~3.2%, Karger's original scheme needs **1000 virtual points per bucket**, and "storing the association requires memory proportional to the number of buckets times the number of points per bucket" — thousands of bytes per candidate shard, megabytes total for a large deployment. [Lamping & Veach, arXiv:1406.2294](https://arxiv.org/pdf/1406.2294), p.2.

### 3.2 Rendezvous / Highest Random Weight hashing (Thaler & Ravishankar, 1996 tech report / IEEE ToN 1998)

HRW needs **no shared state or virtual-node tables at all**: for key `k` and each candidate server `Sᵢ`, compute `Weight(k, Sᵢ)` — a pseudorandom function of the two names — and route to `argmax Weight(k, Sᵢ)`. It is purely a local computation from public names, so "clients can make an immediate decision based on purely local knowledge" with **zero network exchange and zero storage** (§V.A of the paper). The load-balancing quality is provably as good as a fully random assignment, and disruption on membership change is provably bounded between `1/m` and `1` — Theorem 1 in the paper: for any mapping that evenly divides objects among `m` servers, disruption `δ` satisfies `1/m ≤ δ ≤ 1`, and HRW achieves the lower bound. [Thaler & Ravishankar, IEEE/ACM ToN 6(1), 1998](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/02/HRW98.pdf), pp.3, 6.

**Cost:** naive HRW is **O(n)** per lookup — you must evaluate the weight function against every server to find the max. This is the reason jump consistent hash and Maglev exist as *faster* alternatives for the large-n regime, and it is the reason Lamping & Veach call HRW "the only other algorithm we are aware of that computes a consistent hash," immediately following up that a tree-organized variant (Wang et al.) gets lookup to O(log n) "at the cost of balance when shards are added or removed, because [it] only rebalance[s] across the lowest-level nodes of [the] tree" [arXiv:1406.2294, p.3](https://arxiv.org/pdf/1406.2294) — i.e., you can buy back speed but only by giving back Karger's clean monotonicity.

**Why HRW often wins for small N specifically:** dag-worker-go's target instance count (a handful to a few dozen processes per storage cluster, not thousands of cache nodes) is exactly the regime where HRW's O(n) lookup cost is negligible (n ≤ ~64 means a few dozen hash evaluations, sub-microsecond) while its zero-storage, zero-coordination property is a clean win over maintaining a ring or a lookup table at all. This is the deciding factor recommended in §7.

### 3.3 Jump Consistent Hash (Lamping & Veach, Google, 2014)

```c
int32_t JumpConsistentHash(uint64_t key, int32_t num_buckets) {
  int64_t b = -1, j = 0;
  while (j < num_buckets) {
    b = j;
    key = key * 2862933555777941757ULL + 1;
    j = (b + 1) * (double(1LL << 31) / double((key >> 33) + 1));
  }
  return b;
}
```
[Lamping & Veach, arXiv:1406.2294, Fig. 1](https://arxiv.org/pdf/1406.2294)

**Complexity: O(1) space, expected O(ln n) time** — the paper proves the expected number of loop iterations is `< ln(n) + 1`, "fewer expected jumps (by a constant factor) than the log2(n) comparisons needed by a binary search among n sorted keys" (p.5). **Balance quality is essentially perfect**: the paper's own measurement gives Jump Consistent Hash a standard error of **0.00000000764** in per-bucket key-count uniformity versus Karger-with-1000-points-per-bucket's 0.0315723 — four orders of magnitude tighter (Fig. 2, p.6).

**The hard limitation, stated in the abstract itself:** "Its main limitation is that the buckets must be numbered sequentially, which makes it more suitable for data storage applications than for distributed web caching" — i.e., **you cannot remove an arbitrary bucket** (say, instance #7 of 12 crashes) without renumbering; only the highest-numbered bucket can be retired cleanly, because the algorithm's guarantees are proved over the *contiguous range* `[0, num_buckets)`. The paper is explicit that this trades away two of Karger's four consistent-hashing properties (spread, load — both meaningful only when different clients might disagree on the live bucket set) to buy speed, keeping only balance and monotonicity, which is a fine trade *only* if all callers agree on the same live bucket count at all times (p.4) — a strong assumption that requires a serialized membership view, not an eventually-consistent gossip one. This makes it a poor fit for dag-worker-go's instance membership, where crash-and-rejoin at arbitrary index is the normal case, not the exception.

### 3.4 Maglev hashing (Google, NSDI 2016)

Maglev builds a full **lookup table** of size `M` (a prime, chosen much larger than the number of backends — Google's production value is **65537**) up front, rather than computing the target on every lookup. Per backend `i`, two independent hashes give an `offset` and a `skip`; the backend's *preference list* is the permutation `permutation[i][j] = (offset_i + j * skip_i) mod M` for `j = 0..M-1`. The table is then filled by repeatedly walking every backend's preference list in round-robin and giving it the next slot on its list that isn't already taken, until all `M` slots are assigned — guaranteeing every live backend gets `⌊M/n⌋` or `⌈M/n⌉` slots, i.e., **near-perfectly even load**, which the paper prioritizes deliberately over minimal churn: on backend failure, only entries pointing at the failed backend move (≈`M/n` of the table, matching Karger's expected reassignment fraction), and *because permutations are recomputed relative only to a backend's own hash seed*, the assignment for surviving backends is otherwise undisturbed. The distinguishing design choice versus a ring is that Maglev optimizes for **connection-affinity plus even instantaneous load** for an L4 load balancer serving live TCP connections, where Karger's ring only guarantees *eventual* evenness as bucket count grows and can have `Θ(log n)`-factor transient skew from arc-length variance (this is the same skew problem bounded-load hashing in §3.5 fixes directly). [Eisenbud et al., "Maglev," NSDI 2016](https://www.usenix.org/conference/nsdi16/technical-sessions/presentation/eisenbud); construction summarized from [The Paper Trail's walkthrough](https://www.the-paper-trail.org/post/2020-06-23-maglev/), consistent with the abstract's own framing that Maglev "achieve[s] near-perfect load balancing" as the primary design goal.

Maglev's table-rebuild approach is a good fit wherever the assignment set changes rarely and lookups must be single-array-index-fast; it is a *poor* fit for dag-worker-go's instance churn, because a table of size 65537 is total overkill for a few dozen instances and a table rebuild (`O(M)`) on every membership change is disproportionate work for what should be a lightweight event.

### 3.5 Bounded-load consistent hashing (Mirrokni, Thorup, Zadimoghaddam, 2016/2018)

This paper's opening observation is the sharpest indictment of plain consistent hashing for exactly this use case: "the load balancing of [Karger's and Thaler-Ravishankar's] schemes is no better than a random assignment of clients to servers, so with `n` of each, we expect many servers to be overloaded with **Θ(log n / log log n)** clients" (Introduction, p.1) — i.e., plain ring hashing does *not* give you even load, it gives you the same skew as throwing darts, because both a ring's arc-length variance and a fully-random weight function have the same balls-into-bins tail behavior.

**The fix:** fix a load-balancing parameter `c = 1 + ε > 1` (their production recommendation, cited from Vimeo's deployment, is **c = 1.25**). Every bin gets a hard capacity `⌈cm/n⌉`. Balls (here: virtual-partitions, or directly: dag nodes if you skip the intermediate partition layer) are still placed by walking clockwise from their hashed point on the ring, but **if the first bin is full, the ball is forwarded to the next bin, and the next, until it finds one under capacity** — "linear probing by forwarding the ball on the circle to the first non-full bin" (Abstract). This is provably history-independent and gives:

- **Guaranteed max load ≤ ⌈cm/n⌉** (a hard cap, not a probabilistic tail) — Theorem 2/3.
- **Expected O(1/ε²) balls moved when a ball is added or removed**, and **expected O((m/n)/ε²) balls moved when a bin is added or removed** — i.e., rebalancing cost stays close to the theoretical lower bound (`≥ m/n` moves are unavoidable when a bin comes or goes) even while enforcing the hard cap; the paper states this is "only a factor `O(1/ε²)` worse than the general lower bounds without capacity constraints" (§1, p.2).

[Mirrokni, Thorup, Zadimoghaddam, arXiv:1608.01350](https://arxiv.org/pdf/1608.01350)

Two production deployments are cited directly in the paper itself: **Google Cloud Pub/Sub** adopted it to handle its lightly-loaded case (few messages, many partitions) and **Vimeo** adopted it for video-streaming load balancing after "giv[ing] up on traditional consistent hashing and power of two choices because of load balancing problems," reporting `c = 1.25` as "satisfactory" in production at ~1 billion requests/day (§1.3, p.7, citing Rodland's Vimeo engineering blog post).

**Why this is the right knob for dag-worker-go's virtual-partition layer specifically:** the failure mode this paper targets — a `Θ(log n/log log n)` worst-case overload factor from *pure* consistent hashing — is precisely the "one scope is enormous" skew problem from §2, generalized to virtual partitions instead of scopes. Capping partition-count-per-instance with a tunable `c` converts an unbounded skew risk into a bounded, dial-able one, and the *forwarding* mechanism (probe the ring for the next under-capacity bin) is O(1/ε²) expected steps, not O(n) — cheap enough to run on every rebalance tick.

### 3.6 Power-of-two-choices as a lighter-weight alternative/complement (Mitzenmacher, 2001)

Mitzenmacher's supermarket-model result: sending each item to **the less-loaded of two independently, uniformly random choices** (rather than one) drops the expected time an item spends waiting from the `Θ(1/(1-λ))` you get with `d=1` to a bound that decays **doubly exponentially** in the tail — Theorem 1 gives expected wait `≤ Σ λ^{(dⁱ-d)/(d-1)} + o(1)`, and critically the paper's own headline claim is: **"having d = 2 choices leads to exponential improvements in the expected time a customer spends in the system over d = 1, whereas having d = 3 choices is only a constant factor better than d = 2"** — the paper's abstract, verbatim. [Mitzenmacher, IEEE TPDS 12(10), 2001](https://www.eecs.harvard.edu/~michaelm/postscripts/tpds2001.pdf)

This is the theoretical justification for the mitigation in §6.3 (sharding a hot ready-set key into K shards and having claimers pick the least-loaded of two shards instead of one fixed shard) — it is a much lighter mechanism than maintaining a Maglev table or bounded-load ring, requires no membership protocol changes, and is directly applicable *within* whichever partitioning scheme is chosen as a way to further flatten residual hot-spotting on individual shards.

## 4. Work stealing: Cilk and the Go runtime as existence proofs

Work stealing solves a different but related problem: given a fixed pool of workers *inside one process*, how do you keep all of them busy without a shared queue becoming the bottleneck? It's directly analogous to the cross-instance problem if you treat "instance" as "P" and the DAG's ready-set as the pool of runnable work.

**Blumofe & Leiserson, 1999.** Each worker maintains its own **local deque** of ready tasks; a worker that runs dry picks a *uniformly random* victim and steals from the **opposite end** of the victim's deque (steal from the top/head while the owner pushes/pops from the bottom/tail — this asymmetry is what keeps steals and local ops from contending on the same end). The headline theorem: for a "fully strict" (well-structured) computation with total work `T₁` and critical-path length `T∞`, expected execution time on `P` processors is `T₁/P + O(T∞)` — i.e., **provably work-efficient**, with overhead bounded by the DAG's critical path, not by the number of processors or steal attempts. [Blumofe & Leiserson, JACM 46(5), 1999](https://www.csd.uwo.ca/~mmorenom/CS433-CS9624/Resources/Scheduling_multithreaded_computations_by_work_stealing.pdf)

Cilk's runtime implementation (the "THE" protocol, named for its three operations) makes the owner's local push/pop **lock-free and wait-free in the uncontended case**: the owner manipulates the bottom of the deque with plain loads/stores and only falls back to a lock when a steal is racing at the same instant, which is rare because steals target the opposite end. This is the mechanical reason work stealing scales: **the fast path (no contention) touches no shared state at all.**

**The Go runtime scheduler (GMP)** is the same algorithm, in production at enormous scale, and worth citing as a design template rather than merely an analogy, because dag-worker-go is itself a Go library. Each `P` (logical processor) owns a **local run queue (LRQ)** that only the `M` (OS thread) currently bound to it touches — no lock needed on the fast path. When a `P`'s LRQ is empty, the search order is: check the **global run queue** with small fixed probability (Go's runtime source checks it roughly 1-in-61 scheduling ticks, to bound the latency of starvation on the GRQ without paying its lock cost every time); if empty, **steal half the runnable goroutines from a randomly chosen peer P's LRQ** (steal-half, not steal-one — this amortizes the cost of finding a victim over more stolen work and reduces how often stealing needs to recur); if all peers are empty, poll the network poller and finally the GRQ again. To avoid every idle `M` hammering peers simultaneously, only a bounded number of `M`s are allowed to be **spinning** (actively searching for work rather than parking) at once — Go caps spinning `M`s at roughly half the number of busy `P`s, so the search cost is amortized across a bounded number of searchers rather than paid by every idle thread on every scheduling tick. [Ardan Labs, "Scheduling in Go, Part II"](https://www.ardanlabs.com/blog/2018/08/scheduling-in-go-part2.html)

**Why this doesn't transplant directly to cross-process dag-worker-go, and what does:** work stealing's fast path relies on the local deque living in the *same address space* as the owner — the whole point is avoiding a shared-memory round trip. Across processes sharing Redis/Postgres, there is no free local-memory fast path; every "steal" is a network round trip regardless of whether it's framed as stealing or as pull-competition. So work stealing's **exact mechanism** doesn't port, but its **shape** does, and is the core of the recommendation in §7: give each instance a *local, sticky* subset of virtual partitions it services without contention (the Go LRQ analog — implemented as leased partition ownership, §5), and fall back to an explicit, rate-limited "steal" (claim from another instance's leased partitions when your own are empty) only when locally starved — never as the default path. This is materially different from pure pull-competition (§1), where *every* claim pays the shared-key cost regardless of local starvation.

## 5. Membership, epochs, fencing, and the leader-elected alternative

### 5.1 Storage-backed membership (heartbeat rows/keys with TTL) — the recommended default

An instance registers itself by writing a row/key (`{scope-prefix}:members:{instance_id}` in Redis with `PEXPIRE`, or a row with `last_heartbeat` in Postgres) and refreshes it on an interval well under the TTL (classic 3x-heartbeat-to-TTL ratio to tolerate a couple of missed beats from GC pauses or transient network blips). Membership size and list are read by scanning this small set — cheap, because it's bounded by instance count (tens, not millions) not node count. This needs **no new dependency** — it's built entirely on primitives the library already needs for storage (a KV TTL or a SQL row with `now()` comparison), which matters given the brief's requirement to support Redis, Memcached, and Postgres uniformly: Memcached has native TTL (perfect fit for a heartbeat key); Postgres needs a periodic sweep (`DELETE FROM members WHERE last_heartbeat < now() - interval` or a lease-expiry check at read time) since it has no native per-row TTL.

**Failure mode:** false-positive eviction under GC pause or scheduler starvation — an instance that's alive but hasn't refreshed in time gets treated as dead and its partitions reassigned; when it resumes, it must be prevented from acting on stale state. This is exactly what fencing (§5.4) exists to close, and it's why membership alone is never sufficient — a membership protocol tells you who *should* own what; it cannot by itself stop a wrongly-still-alive instance from acting anyway.

**This is not a novel pattern — it's how AWS's own Kinesis Client Library (KCL) coordinates sharded stream consumption today.** KCL stores one row per shard in a DynamoDB **lease table**; the row records the current `leaseOwner` and a `leaseCounter`, workers periodically **heartbeat** (renew) the leases they hold, and "when a worker stops holding a lease due to stopping or failing, KCL assigns another worker to take the lease" by another worker claiming the now-stale row once its heartbeat has visibly lapsed — the same storage-backed-heartbeat-plus-takeover shape recommended here, with `leaseCounter` serving as exactly the fencing epoch of §5.4 (a worker whose lease was stolen and whose counter has since moved on is rejected if it tries to write with a stale counter value). [AWS: KCL concepts — Lease, Lease table](https://docs.aws.amazon.com/streams/latest/dev/kcl-concepts.html) This is direct industrial precedent, at meaningful production scale, for building cross-instance partition ownership entirely out of a plain database table plus a counter — no gossip, no consensus cluster, exactly the shape §7 recommends.

### 5.2 Real consensus (Raft/Paxos via etcd or ZooKeeper) — explicitly rejected as a default dependency

The heaviest-weight option is to run membership and partition assignment through a real consensus system — a ZooKeeper ensemble (as Kafka historically used for controller election and, in older versions, consumer group coordination) or an etcd/Raft cluster (as Kubernetes uses for all cluster state). Consensus buys the strongest possible guarantee — a linearizable, globally-agreed membership view with no risk of two nodes disagreeing about who owns what, even transiently — which sounds like exactly what §5.1's storage-backed heartbeats give up (a heartbeat-TTL view is only eventually consistent: two instances can briefly disagree about whether a third is alive, right around the TTL boundary). Chubby's own paper argues precisely for consensus-backed coarse-grained locking as the way to give ordinary lock-based programmers "a significant improvement in availability in systems that no longer required human intervention on failure" (§1) — and Chubby's leases are themselves layered on Paxos.

**Why reject it as the default here anyway:** every consensus system pays its safety with an *operational* dependency the brief explicitly rules out — a Raft or ZooKeeper ensemble is a separate stateful cluster (typically 3 or 5 nodes) that the host program must now deploy, monitor, and keep quorum-healthy, entirely independent of whichever of Redis/Memcached/Postgres the host already chose as dag-worker-go's storage backend. That's a second distributed system to operate solely to answer "which instances are alive" — a question a TTL'd row in the storage backend the host is *already running* answers adequately at this library's scale. Consensus is the right call when the cost of a wrong membership decision is catastrophic and un-fenceable (leader election for a single source of truth, e.g. who is allowed to be the Postgres primary) — it is not the right call for "which instance should preferentially claim from which partition," a decision this design has already made cheap to get wrong: §5.4's fencing epoch means a stale membership view causes at most a wasted claim attempt or a redundant scan, never a correctness violation, which removes the one reason strong consensus would otherwise be worth its operational weight.

### 5.3 Gossip (SWIM / hashicorp/memberlist) — explicitly rejected as a default dependency

SWIM (Das, Gupta, Motivala, 2002) decouples failure detection from dissemination: a node picks a random peer, pings it directly, and if it times out asks `k` other random peers to ping it indirectly (working around a single slow network path false-positiving a live node) — its headline property is that "the expected time to first detection of a failure, the false positive rate, and the message load per group member are **independent of group size**," which is what lets it scale to thousands of nodes without a coordinator. [Das, Gupta, Motivala, SWIM, DSN 2002](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf) `hashicorp/memberlist` is the production Go implementation, adding the **Lifeguard** extensions for robustness under slow message processing, and describes itself as "eventually consistent but converg[ing] quickly." [hashicorp/memberlist](https://github.com/hashicorp/memberlist)

**Why reject it as the default:** SWIM's entire value proposition is scaling failure detection to cluster sizes where an O(n²) all-to-all heartbeat is infeasible — hundreds to thousands of nodes. dag-worker-go instance counts are realistically single digits to low hundreds per storage cluster; a heartbeat-row-with-TTL scan of the members table is O(instance count) and stays comfortably under any latency budget at that scale, for zero added dependency, zero added network protocol, and zero added operational surface (no UDP gossip ports to open, no separate cluster to reason about during network partitions). Gossip membership is the right call when membership size itself threatens to be the bottleneck; it never becomes the bottleneck at the scale this library's brief describes, and pulling in a gossip layer purely for "not storage-backed" purity would violate the "no heavy dependency" instruction directly. Keep it as a **documented alternative membership provider** behind the same interface, for the specific host program that already runs a memberlist/Serf/Consul cluster and wants dag-worker-go to reuse it instead of adding storage-backed heartbeats — but ship storage-backed as the only built-in.

### 5.4 Fencing tokens — the mechanism that makes any partitioning scheme safe

Kleppmann's canonical argument: a lease alone (TTL-bounded ownership) doesn't stop a holder that GC-pauses past its lease expiry from resuming and acting as though it still owns the resource — "a holder that pauses for longer than the lease TTL has implicitly lost the lease but has no immediate way to know," and "no lock implementation... can guarantee mutual exclusion in the presence of arbitrary process pauses without fencing." The fix moves the check to the *resource*, not the holder: every lease grant carries a **monotonically increasing token**; every write the holder makes to the protected resource carries that token; the resource **rejects any write whose token is lower than the highest it has already seen**, unconditionally, even from a technically-still-executing writer. [Kleppmann, "How to do distributed locking," 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)

**Chubby is the production-grade version of exactly this,** and its rationale for existing at all is directly relevant to why dag-worker-go should build fencing in rather than treat locking as a client-library nicety: "many programmers have come across locks before... Ironically, such programmers are usually wrong, especially when they use locks in a distributed system; few consider the effects of independent machine failures on locks." Chubby's sequencer mechanism is the fencing token by another name: "a lock holder may request a *sequencer*, an opaque byte-string that describes the state of the lock... it contains the name of the lock, the mode in which it was acquired..., and **the lock generation number**"; the recipient of a request "is expected to test whether [the sequencer] is still valid... if not, it should reject the request." Chubby further layers on a **lock-delay** (default configurable up to 1 minute) during which a lock that was force-released or lost to failure cannot be reacquired by *anyone*, specifically to protect servers that can't check sequencers from acting on stale requests still in flight from the previous holder — a pragmatic admission that fencing-at-the-resource isn't always retrofittable, so a time buffer covers the gap. [Burrows, "The Chubby lock service," OSDI 2006](https://static.googleusercontent.com/media/research.google.com/en//archive/chubby-osdi06.pdf), §2.1, §2.4.

**Concretely for dag-worker-go:** every claim of a partition (or, in the simple v0.1 design, every claim of a node directly) must carry an **epoch/generation number** that increases monotonically each time ownership of that partition changes hands. The claim write is a single atomic compare-and-swap conditioned on that epoch:

```sql
-- Postgres: claiming a partition lease with a fencing epoch
UPDATE partition_leases
SET    owner = $1, epoch = epoch + 1, lease_until = now() + $2
WHERE  partition_id = $3
  AND  (owner IS NULL OR lease_until < now())   -- only steal a truly expired lease
RETURNING epoch;
```
```lua
-- Redis: same operation via Lua for atomicity
-- KEYS[1] = partition lease hash key
-- ARGV[1] = new owner id, ARGV[2] = lease TTL seconds
local owner = redis.call('HGET', KEYS[1], 'owner')
local lease_until = tonumber(redis.call('HGET', KEYS[1], 'lease_until') or '0')
if owner == false or lease_until < tonumber(ARGV[3]) then
  local epoch = tonumber(redis.call('HGET', KEYS[1], 'epoch') or '0') + 1
  redis.call('HSET', KEYS[1], 'owner', ARGV[1], 'epoch', epoch,
             'lease_until', ARGV[3] + tonumber(ARGV[2]))
  return epoch
end
return nil
```

Every subsequent node-status write made by the holder of that partition is tagged with the epoch it claimed under; the storage layer's node-update path rejects (or logs-and-drops) any write whose epoch is lower than the partition's current epoch. This closes the split-brain hazard from §2 and §3 identically regardless of which partitioning scheme is chosen — it is the one piece of machinery that is *not* optional and *not* partitioning-scheme-specific.

### 5.5 Leader-elected single dispatcher — why it caps throughput, and when it's still right

Airflow's classic (pre-2.0) architecture ran exactly one active scheduler; HA was bolted on later (AIP-15) by letting multiple schedulers run concurrently against the same metadata DB with row-level locking arbitrating, specifically *because* a single scheduler process parsing every DAG file and issuing every task instance became the throughput ceiling as DAG count grew — Airflow's own docs on tuning acknowledge a direct trade: raising `max_dagruns_per_scheduling_loop` "will allow more throughput for smaller DAGs but will likely slow down throughput for larger (>500 tasks) DAGs" scheduled by one process. A single elected dispatcher is architecturally simple (no partition scheme, no fencing needed beyond the leader election itself, trivial to reason about for correctness) but its throughput is capped at whatever one process, one core-bound loop, and one connection pool to storage can push — it cannot be scaled by adding instances, only by making the one instance faster. It caps throughput by construction, not by tuning: the whole redesign in Airflow 2.0 and later was specifically to *escape* that cap. [Apache Airflow scheduler docs](https://airflow.apache.org/docs/apache-airflow/stable/administration-and-deployment/scheduler.html)

**When it's still the right call:** never as the steady-state dispatch path for dag-worker-go given the brief's explicit "multiple instances working concurrently" requirement and the performance-is-a-headline-goal framing — but it remains the right shape for a *narrow, low-frequency, globally-serialized* task that genuinely must not run twice: e.g., "run the periodic sweep that finds and re-queues nodes stuck in-progress past their timeout" (§ of the state-machine spec, not this document) is a good candidate for a leader-elected singleton, because it's infrequent, cheap, and its correctness is much easier to reason about with one actor than with N racing sweepers deduplicating via fencing. Use leader election as a *targeted tool for specific maintenance tasks*, never as the work-dispatch mechanism itself.

## 6. Quantifying contention

### 6.1 Redis: how fast does one key/list become the bottleneck?

Redis is single-threaded for command execution (multi-I/O-thread since 6.0 is for network I/O, not command dispatch), so every command against one key is fully serialized against every other command on that key by construction. Baseline single-instance Redis throughput for simple `GET`/`SET`-class commands is commonly cited in the **100K–200K ops/sec** range on modern hardware; the number that matters for a shared ready-list is narrower — one blocking-pop-style claim against one list is one round trip, so realistic sustained claim throughput against **one** hot list/key, accounting for network RTT and Lua-script overhead for atomic claim-plus-bookkeeping (as Asynq's `dequeueCmd` does), lands in the **tens of thousands of claims/sec** ballpark before the single key's serialization becomes the visible ceiling, well below Redis's raw per-command ops/sec because each claim is doing more than one bare command's worth of work. This is corroborated qualitatively rather than by one canonical benchmark: multiple independent sources converge on Redis-backed queue systems "shining in the 10k–100k msg/sec range" per stream/list, with the low end dominated by script/round-trip overhead and the high end approached only with pipelining or batching multiple items per claim — which a fair-dispatch DAG scheduler generally cannot do freely, since claims are typically one-node-at-a-time to respect priority and dependency ordering.

### 6.2 PostgreSQL: `SELECT ... FOR UPDATE SKIP LOCKED` throughput and its degradation modes

`SKIP LOCKED` turns lock contention from *blocking* into *wasted CPU scanning past locked rows* — better than blocking, but not free: "with high concurrency, many workers end up scanning past the same locked rows before finding one they can claim... this is wasted CPU," and independently, "with thousands of concurrent transactions, the ProcArray... becomes a contention point itself" via `ProcArrayLock` waits. Reported real numbers: one head-to-head benchmark measured **~28% end-to-end throughput improvement** from adding `FOR UPDATE SKIP LOCKED` versus a naive polling claim; separately, a stress test that deliberately held back the transaction horizon (a long-running transaction preventing vacuum from reclaiming dead tuples) found dead-tuple count in the queue table grow **14×**, table size grow **15×**, dequeue throughput **drop ~35%**, and unrelated-table query latency sharing the same buffer cache rise **~50%** — i.e., the SKIP-LOCKED-queue pattern degrades gracefully under moderate concurrency but is acutely sensitive to autovacuum falling behind, which a high-claim-rate job table is prone to precisely because every claim is an `UPDATE` generating a dead tuple. Graphile-worker (a comparable Postgres-backed queue) is independently cited as topping out around **100–200 jobs/second** on typical hardware before lock contention dominates — a useful order-of-magnitude anchor: Postgres-as-queue is roughly **2–3 orders of magnitude** below a Redis list for pure claim throughput on one table/key, which is the central quantitative reason to shard the ready-set (§6.3) far more aggressively on the Postgres backend than on Redis, and to keep autovacuum tuned aggressively on whatever table backs the ready-set (more aggressive `autovacuum_vacuum_scale_factor`, or an `UNLOGGED` staging table for ready-state if durability requirements allow it).

### 6.3 Sharding the ready-set into K shards, and the empty-shard/starvation problem

The fix for both backends is structural, not a backend-specific tuning knob: split one hot ready-set key/table into **K independently-claimable shards** (`ready:0` … `ready:K-1` in Redis; `ready_shard` column with `SKIP LOCKED` scoped per-shard-range in Postgres), and have each claimer pick a shard rather than always hitting shard 0. This converts one serialization point into K, multiplying throughput ceiling by roughly K — but naive uniform-random shard selection reintroduces two problems:

1. **Empty-shard waste.** If a claimer picks a shard uniformly at random and that shard happens to be drained (its ready nodes already claimed), the claim attempt is wasted work — the claimer must retry against a different shard, and worst-case behavior under bursty, uneven arrival (a DAG that just unblocked 50 nodes into shards 3 and 7 while shards 0–2 and 4–6 sit empty) degenerates toward the throughput of blind polling.
2. **Starvation skew.** If shard selection is sticky (fixed per-instance, as in static partitioning, §2) rather than random-per-claim, an instance mapped to a perpetually-empty shard starves while another instance's shard backs up — the exact head-of-line problem from §2, just at finer grain.

**Mitzenmacher's power-of-two-choices result (§3.6) is the standard fix for both:** rather than picking one shard at random, a claimer checks the approximate depth (or simply attempts a non-blocking claim, treating "empty" as depth 0) of **two** independently-random shards and claims from whichever is non-empty / deeper, falling back to the other if the first is empty. Because the theoretical result shows `d=2` gives an *exponential* improvement in tail wait time over `d=1` while `d=3` only buys a further constant factor, **two shard probes is the correct operating point** — it captures nearly all the achievable benefit for the added cost of one extra round trip, and adding a third probe is not worth the marginal round trip. In Redis this is a single Lua script doing `LLEN` (or checking a small approximate counter to avoid an O(n) `LLEN` on a list — better: maintain a per-shard approximate depth as a separate `INCR`/`DECR` counter) on two candidate shard keys and popping from the non-empty one; in Postgres it's two `SELECT count(*) FROM ready WHERE shard = $s` estimates (or, cheaper, two speculative `SKIP LOCKED` claim attempts in sequence, accepting the first success) against two candidate shard partitions.

**Choosing K:** K should scale with expected peak concurrent claimers, not with node count — a good starting point is `K ≈ 4–8× max expected concurrent instances`, giving enough shards that two random probes rarely both land on empty shards under normal load, while keeping K small enough that per-shard bookkeeping (Redis: K list keys; Postgres: a `shard` column plus a partial index) stays cheap. This directly reuses the bounded-load consistent hashing capacity parameter `c` (§3.5) if virtual partitions and ready-set shards are unified into one layer, which is exactly the recommendation in §7.

## 7. Recommended design

### 7.1 The hybrid, precisely

**Layer 1 — Membership.** Storage-backed heartbeat rows/keys per instance, TTL = `3× heartbeat_interval` (default heartbeat interval 2s → TTL 6s, both configurable). No gossip, no consensus dependency. Exposed behind an interface so a host program that already runs Consul/Serf/memberlist can plug that in instead.

**Layer 2 — Virtual partitioning.** Fix `P` virtual partitions per scope at scope-creation time (default `P = 64`, configurable per scope for scopes known upfront to be huge) — sequential integer ids `0..P-1` (not consistent-hash points), because within a *single* scope the partition count for that scope is centrally known and rarely changes, so jump-consistent-hash-style sequential numbering (§3.3) is an acceptable and cheap fit for **mapping node → virtual partition**: `partition = JumpConsistentHash(hash(node_id), P)`. This gives O(1)-space, O(log P) expected time, near-perfect balance of *nodes* across partitions — exactly the property jump consistent hash is best at, and its "can't remove an arbitrary bucket" limitation doesn't bite here because node→partition assignment is fixed once `P` is fixed; only partition→instance assignment ever changes.

**Layer 3 — Partition-to-instance assignment.** This is the layer that changes on membership churn, and it's where HRW (§3.2), not jump consistent hash, is the right tool, precisely because instances *do* leave and rejoin at arbitrary points, not just at the end of a sequence: for each of the `P` (typically 64) partitions, compute `argmax_instance Weight(partition_id, instance_id)` over the *currently live* instance set (from Layer 1's membership view). `P` is small (tens to low hundreds even across many scopes if partitions are pooled) and the live instance count is small (tens), so HRW's O(n) cost per lookup is microseconds, it needs zero coordination or shared table, and its disruption on membership change is provably bounded at the `1/m` optimum (§3.2, Theorem 1) — every instance computes the same assignment independently from the same (membership-view, partition-id) inputs with no message exchange, avoiding a rebalance protocol entirely. Layer bounded-load capacity (§3.5, `c ≈ 1.25–1.5`) on top of the same weight function if empirical skew across partitions (some partitions consistently busier) turns out to matter — cap how many partitions each instance's HRW ranking may win before forwarding to the next-highest-weight instance, exactly as Vimeo did for its ring.

**Layer 4 — Claiming within an owned partition.** Once an instance owns partition `k` (by the Layer 3 computation, refreshed on every membership-view change), it claims nodes from that partition's ready-set using the backend-appropriate atomic primitive (Redis: `RPOPLPUSH`-into-active-plus-lease-ZADD as Asynq does, or `XREADGROUP` if Streams are used; Postgres: `FOR UPDATE SKIP LOCKED` scoped `WHERE partition = k`). Every claim carries the fencing epoch (§5.4) for partition `k` at time of claim; every subsequent status-transition write for that node is tagged with that epoch and rejected by storage if a newer epoch for partition `k` has since been granted to a different instance. This is the direct analog of the Go scheduler's local-run-queue fast path (§4): the common case touches only the state for partitions you already own, no shared hot key, no contention with other instances.

**Layer 5 — Stealing, for the empty-local-queue case.** When an instance's owned partitions are all empty (no ready nodes) but the aggregate ready-set across all partitions is non-empty (visible via a lightweight per-partition approximate-depth counter, maintained the same way as the shard-depth counters in §6.3), it may **steal**: attempt a claim against a partition it doesn't own, using the two-random-choices rule from §3.6/§6.3 (probe two non-owned partitions' depth counters, attempt the deeper one) rather than scanning all `P` partitions. Because the underlying claim primitive (Layer 4) is a storage-level atomic operation independent of who "owns" the partition, a steal is exactly as safe as a claim by the rightful owner — ownership in this design is a *routing optimization to avoid contention*, never a correctness boundary; correctness is entirely carried by the fencing epoch on the node-status write, which is the same invariant established in §2 for scope-based static partitioning and generalizes cleanly.

### 7.2 Why each rejected alternative loses, stated directly

- **Pure pull-competition alone (§1)** is rejected as the *only* mechanism because it gives up all locality — every claim is a cold storage round trip with no in-memory index reuse, which directly conflicts with the O(1)/O(log n) mandate at 1M-node scale; it remains, nested inside Layer 4, as the *correct* primitive for claiming within a partition, and as the *entire* mechanism for the simple v0.1 (§7.3).
- **Static scope partitioning alone (§2)** is rejected because scope-size skew is a certainty in a multi-tenant DAG library (one customer's batch job dwarfs another's), and a hard 1:1 scope-to-instance mapping cannot borrow idle capacity across scopes; virtual partitioning subsumes it as a special case (a scope can simply be given many virtual partitions if it's known to be large) without the head-of-line problem.
- **Maglev's table approach (§3.4)** is rejected for partition→instance assignment specifically because it optimizes for a regime (huge, rarely-changing backend set, millions of lookups/sec against a static table) that doesn't match dag-worker-go's regime (tens of instances, membership genuinely churns); rebuilding an `O(M)` table on every join/leave for `M` in the tens-of-thousands range is disproportionate machinery for tens-of-partitions-scale problems that HRW solves with zero table at all.
- **Jump consistent hash for partition→instance assignment (§3.3)** is rejected for that specific role — its own paper says so — because instances can leave at arbitrary index, not just the top of a sequence; it's kept, correctly, for the node→partition layer where the assignment is append-only and instance-agnostic.
- **Work stealing's literal mechanism (§4)** is rejected as a cross-process primitive because there is no shared-memory local deque to give it a lock-free fast path across process boundaries — every "steal" and every "local pop" cost the same network round trip, collapsing the reason work stealing beats plain sharing in the first place; its *shape* (sticky local ownership, steal only when locally starved, steal in bulk/probabilistically rather than scan-everything) is retained as Layers 4–5.
- **Leader-elected single dispatch (§5.5)** is rejected as the work-distribution mechanism because Airflow's own history is a documented case study of exactly this cap being hit and specifically re-architected away from; it is retained narrowly for a periodic timeout-sweep maintenance task, where single-actor simplicity outweighs the (here, negligible) throughput cost.
- **Gossip membership (§5.3)** is rejected as the default for the same reason real consensus is (§5.2) — a scaling problem it solves (O(n²) heartbeats at thousands of nodes) that dag-worker-go doesn't have at its target instance counts, and the brief explicitly asks to avoid adding a heavy dependency; kept as a pluggable alternative for hosts that already run one.

### 7.3 Migration path: v0.1 simple → sophisticated, with no API break

The public API host programs see is: subscribe to a status-transition/dispatch event stream, claim/ack/error a node, done. None of Layers 1–5 need to be visible in that surface, which is what makes a staged rollout possible.

**v0.1 — ship Layer 4 alone, `P = 1` implicit.** Every node in a scope is claimable by every instance via the plain atomic-claim primitive (`SKIP LOCKED` / `RPOPLPUSH`-plus-lease) directly against the scope's single ready-set, no partition concept exposed even internally beyond a constant `P=1`. This is correct, is exactly the pattern every production system surveyed in §1 ships as its baseline, and needs no membership table, no fencing epoch beyond a per-node claim token (a simple `claimed_by + claim_deadline` pair, which the brief's "settable per-node timeout" requirement needs anyway regardless of partitioning strategy).

**v0.2 — introduce `P > 1` virtual partitions and Layer 1 membership, keep assignment trivial.** Add the node→partition hash (Layer 2) internally; assignment (Layer 3) starts as the simplest possible correct rule — e.g., `instance_index = live_instances_sorted_by_id[partition mod len(live_instances)]` — recomputed on every membership-view refresh. This is strictly worse load-balancing than HRW under churn but is a two-line function, validates the plumbing (fencing epoch per partition, membership heartbeats, partition-scoped claim queries) end-to-end before investing in the fancier assignment math. No public API change: claim/ack/error calls are unchanged; only the internal routing of *which* partition's ready-set a given claim attempt polls changes.

**v0.3 — swap the assignment function for HRW (§3.2) plus bounded-load capping (§3.5), add Layer 5 stealing.** Because Layer 3's assignment function is already an internal, swappable component as of v0.2, replacing the naive modulo rule with HRW is an internal refactor, not an API change — the only externally observable effect is smoother rebalancing (provably bounded disruption instead of the modulo rule's potential for reassigning everything on any membership change, since `mod len(live_instances)` reshuffles almost every partition when the instance count changes, exactly the problem consistent hashing exists to solve). Add the two-random-choices steal path (§6.3) once real workloads show idle instances beside backlogged ones.

**Never a breaking change, because:** the fencing epoch (§5.4) is present from v0.1 (as a per-node claim token) and is the *only* thing status-write correctness ever depends on; partitioning, membership, and assignment are pure internal routing/optimization layers added underneath a claim API whose contract ("give me a node currently in `ready`, tell me when to give up on me") never changes shape. This is the same reason Kafka's KIP-848 rebalance-protocol rewrite (§ below) could ship as a protocol-version negotiation rather than a client API break: the *what* (claim/ack/assignment) stayed stable while the *how* (rebalance mechanics) was swapped underneath. [KIP-848](https://cwiki.apache.org/confluence/display/KAFKA/KIP-848%3A+The+Next+Generation+of+the+Consumer+Rebalance+Protocol) is itself worth citing as the industrial precedent for this exact migration shape: it replaced a "stop the world" synchronized-barrier rebalance (structurally similar to v0.2's crude reassignment) with per-member independent reconciliation driven by a group epoch (structurally similar to v0.3's HRW-plus-fencing), and did so as an opt-in protocol upgrade specifically so existing consumer clients kept working unmodified.

## Open questions

- **Cross-backend fencing-epoch semantics.** Postgres gives cheap monotonic epochs via a single-row `UPDATE ... RETURNING`. Redis gives the same via `INCR`. Memcached has `incr`/`decr` but no atomic compare-and-swap on the epoch *and* ownership fields together without `cas` tokens with narrower semantics than Redis's Lua scripts or Postgres's transactions — the exact Memcached-specific claim protocol (likely: separate `add` for ownership plus `cas`-looped epoch bump) needs its own dedicated design pass and a note on what invariants weaken on that backend specifically.
- **Cross-scope partition pooling.** §7.1 assumes partitions are namespaced per-scope (`P` per scope). Whether to instead pool virtual partitions *across* scopes on one instance-assignment ring (fewer, larger scopes sharing partitions with many small scopes) trades simpler bookkeeping against the loss of per-scope capacity isolation (one giant scope's partitions competing for instance-assignment weight against many tiny scopes') — needs a decision informed by the actual multi-tenancy shape once real workloads exist.
- **Depth-counter staleness under the two-random-choices steal path.** The approximate per-partition depth counters proposed in §6.3/§7.1 Layer 5 will drift under concurrent claim/enqueue; how much drift is tolerable before power-of-two-choices' benefit erodes back toward uniform-random choice hasn't been measured for this workload's specific arrival pattern (bursty, dependency-driven, not Poisson) — Mitzenmacher's own result assumes Poisson arrivals, and DAG unblocking is not Poisson.
- **HRW recomputation cost at the high end of scope-partition-count growth.** §7.1 assumes `P` in the tens-to-hundreds range keeps HRW's O(n) evaluation cheap; if a future requirement pushes total pooled partitions into the thousands (many large scopes), HRW's O(n) per-partition lookup, done for every partition on every membership change, becomes the cost center Maglev exists to avoid — the crossover point where Maglev's O(M)-rebuild-but-O(1)-lookup trade starts winning over HRW's O(n)-lookup-but-zero-storage trade should be benchmarked, not assumed, before committing past v0.3.
- **Whether the leader-elected timeout sweep (§5.5) itself needs a fencing epoch.** If a leader-election implementation has a window where two instances can both believe they're the sweep leader (any lease-based election with a network partition), the sweep's own writes (reclaiming timed-out nodes) need the same node-level fencing-epoch protection as ordinary claims — this should be verified explicitly against whatever leader-election primitive is chosen, not assumed safe because "there's only one leader."

## Recommendations for dag-worker-go

1. **Adopt the fencing epoch as a day-one primitive, independent of everything else in this document.** Every node carries `claimed_by`, `claim_epoch`, `claim_deadline`; every status-transition write is conditioned on `claim_epoch = expected`. This is required regardless of which partitioning strategy ships when, it is cheap on every backend, and retrofitting it after v0.1 ships is far more painful than including it from the start — build it before building anything else in this document.
2. **Ship v0.1 as pure pull-competition (§1/§7.3) — no partitioning, no membership table, no leases beyond the per-node claim token.** It is correct, it is what nearly every production system surveyed here ships as a baseline, and it validates the storage-adapter interface (Redis/Postgres/Memcached each need one atomic-claim implementation) before any partitioning complexity is layered on.
3. **Design the internal partition-assignment function as a swappable interface from the very first line of code that touches it, even while v0.1's implementation is the trivial `P=1` case** — this is what makes the v0.2→v0.3 upgrade non-breaking; do not let "assignment" leak into the public claim API's shape at any point.
4. **When partitioning ships (v0.2+), use jump consistent hash for node→partition (append-only, instance-agnostic) and HRW for partition→instance (handles arbitrary join/leave) — not the same algorithm for both layers.** They solve different problems (§3.3 vs §3.2) and conflating them (e.g., using jump hash for instance assignment, where instances leave at arbitrary points) reintroduces the exact failure mode jump hash's own paper warns against.
5. **Benchmark the Postgres backend's `SKIP LOCKED` claim throughput explicitly against autovacuum aggressiveness settings before finalizing the 1M-node benchmark methodology** — §6.2's cited degradation modes (14× dead-tuple growth, 35% dequeue throughput drop) are autovacuum-lag artifacts, not `SKIP LOCKED` artifacts per se, and are avoidable with `autovacuum_vacuum_scale_factor` tuned aggressively on the ready-set table specifically; failing to control for this will make Postgres look artificially worse than Redis in the mandated benchmark suite.
6. **Default the ready-set shard count / virtual-partition count `P` to something in the 32–64 range per scope, not 1 and not thousands** — low enough that HRW recomputation and per-partition bookkeeping stay cheap, high enough that a handful of concurrent instances rarely collide on the same partition, consistent with the two-random-choices sizing rule in §6.3.
7. **Treat leader election as a tool reserved for the timeout-sweep maintenance path only, never as the work-dispatch mechanism** — Airflow's own architectural history (§5.5) is the cautionary tale to point to explicitly in the library's own ADR when this decision is questioned later.
